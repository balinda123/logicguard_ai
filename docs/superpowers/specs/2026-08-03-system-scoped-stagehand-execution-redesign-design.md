# 系统级测试设计与 Stagehand 执行架构重构设计

> 状态：已确认，尚未实现
> 日期：2026-08-03

## 1. 背景与问题

当前产品以“用例”为主要隔离维度，缺少稳定的系统归属。测试设计的需求、生成用例、检查确认和回归执行又分别保存在不同的页面状态或数据结构中，造成以下问题：

- 同一系统的需求、用例、套件、账号和执行记录没有统一归属，未来增加多个被测系统后容易混用数据。
- 四步测试设计是松散向导：需求来源未持久化，但后续步骤可显示上次生成结果，页面状态与真实数据不一致。
- 执行任务由页面组件持有，切换左侧导航会卸载组件并中断或丢失执行控制。
- 新执行链缺少完整的暂停、继续和终止能力，旧控制台虽有按钮，但没有接入当前执行任务。
- 浏览器执行期间没有明确的受控标识和交互保护，用户操作可能破坏自动化现场。
- AI 生成的临时脚本可能把普通文本当作 CSS 选择器，导致 `querySelector` 语法错误。
- 密码占位符可能作为普通文本传入 AI 和浏览器，例如 `{{employeePassword}}`，既无法登录，也突破凭据边界。
- 模型网关返回 HTML、限流或超时时，错误被混入业务执行结果，任务可能卡住或错误地产生缺陷。
- 执行记录分散在 SQLite、JSON 文件和 localStorage 中，导致执行完成但测试报告页不可见。
- 现有 UI 把过程步骤当成长期数据结构，缺少可回看、可版本化的测试设计实体。

## 2. 目标

本次重构必须实现：

1. 引入系统级数据归属，但仅“测试设计”页面按当前系统和环境展示数据。
2. 保留需求来源、生成用例、检查确认、回归配置四个业务阶段，并将其组织为可持久化、可版本化的测试设计生命周期。
3. 将执行任务迁移到 Rust 后台运行管理器，使切页、刷新和前端重建不影响任务。
4. 仅保留 Stagehand v3 作为浏览器自动化 SDK，消除并行维护的直接 Playwright、自定义 CDP 和多套执行器。
5. 提供明显且可靠的浏览器受控状态、暂停、继续、人工接管和终止能力。
6. 将账号凭据完全隔离于 AI、用例、脚本、日志、截图文本和报告之外。
7. 统一执行结果和报告存储，保证所有终态任务可查询、可追溯。
8. 保留现有数据并完成可验证迁移，不静默删除历史数据。

## 3. 非目标

- 本期不增加预发、生产等环境类型，只支持“本地”和“测试”。
- 本期不把任务控制台、执行中心、测试报告、问题跟踪和系统设置拆成单系统页面。
- 本期不让 Stagehand agent 自主决定登录凭据、任务生命周期、缺陷分类或跨系统执行策略。
- 本期不要求并行控制多个测试浏览器。单个专用浏览器同时只执行一个活动任务，其余任务排队。
- 本期不删除尚未完成迁移验证的旧数据或备份。

## 4. 信息架构

### 4.1 全局页面

以下页面展示所有系统的数据，通过筛选器区分系统、环境、状态和时间：

- 任务控制台
- 执行中心
- 测试报告
- 问题跟踪
- 系统设置

全局页面中的每条记录必须显示系统和环境，且可回到对应测试设计。

### 4.2 按系统隔离的页面

只有“测试设计”按当前系统和环境加载数据。页面顶部提供系统选择器和环境选择器，切换后整个设计列表和详情同步切换，不混合展示。

环境类型固定为：

- `local`：开发人员本地启动的被测应用。
- `test`：产品、测试等角色使用的共享测试环境域名。

数据模型保留环境类型扩展能力，但 UI 和校验在本期只允许上述两种类型。

## 5. 测试设计生命周期

### 5.1 核心实体

新增 `TestDesign` 聚合，作为四个业务阶段的持久化载体。一个系统环境可包含多个测试设计，每个测试设计通过 `designId` 关联：

- 需求版本
- 用例生成批次
- 测试用例
- 检查与确认记录
- 回归配置
- 执行批次和报告

页面结构改为“测试设计列表 + 设计详情”。四个阶段不删除，但不再作为互相独立的临时页面状态。

### 5.2 四个阶段

1. **需求来源**：保存需求正文、来源、附件引用和版本。需求不能为空时，后续生成动作才可用。
2. **生成用例**：基于指定需求版本生成批次，并记录模型、模板、生成时间和来源版本。
3. **检查确认**：记录确认人、确认时间、修改摘要和风险结论；只允许已确认用例进入默认回归范围。
4. **回归配置与启动**：配置套件、账号角色组合和执行范围，创建后台执行任务；真实运行与控制统一进入全局执行中心。

### 5.3 版本规则

- 编辑需求创建新版本，不覆盖旧版本。
- 新需求版本产生后，基于旧版本生成的用例标记为“来源已过期”，但仍可查看和追溯。
- 重新生成创建新批次，不覆盖旧批次。
- 执行任务保存启动时的系统、环境、需求版本、设计、套件、用例和账号角色快照，后续编辑不改变历史结果。
- 没有需求来源的既有用例迁入“历史导入设计单”，而不是伪造需求。

## 6. 数据模型

SQLite 作为唯一持久化事实来源。主要实体包括：

- `systems`：被测系统。
- `system_environments`：系统环境，类型为 `local` 或 `test`，包含基础 URL 和启用状态。
- `test_designs`：测试设计主记录，归属系统和环境。
- `requirement_versions`：需求版本及来源信息。
- `generation_batches`：用例生成批次及输入版本快照。
- `test_cases`：用例，关联设计、需求版本和生成批次。
- `review_records`：检查确认记录。
- `regression_configs`：套件、范围、角色组合等回归配置。
- `accounts`：账号元数据，只保存角色、环境、登录方式和 `credentialRef`。
- `account_combinations`、`scenarios`、`suites`：全部增加系统和环境归属。
- `runs`：后台执行任务及启动快照。
- `run_case_results`：用例级结果和失败分类。
- `run_events`：状态变化、步骤、重试、暂停和人工接管事件。
- `run_evidence`：截图等证据的元数据引用。
- `reports`：统一报告索引和汇总。
- `issue_drafts`：仅由业务断言失败创建的待确认缺陷。

所有跨实体写入必须校验 `systemId` 和 `environmentId` 一致性，禁止把不同系统或环境的账号、套件、用例组合到同一执行任务。

## 7. Stagehand 单一浏览器执行栈

### 7.1 分层职责

执行链统一为：

`Rust 后台运行管理器 -> Stagehand v3 -> 专用测试浏览器`

Stagehand 能力按确定性优先使用：

- `Page` / `Locator`：执行已编译、可验证的确定性步骤。
- `observe`：为语义目标发现稳定候选定位。
- `act`：执行边界明确的单个 AI 操作。
- `agent`：只处理无法预编译的有限多步任务，并受步骤数、域名、超时和动作类型约束。

Stagehand v3 的原生 CDP 引擎作为底层连接能力。应用不再直接维护另一套 CDP 控制器。Playwright 仅可作为迁移期对照测试工具，不作为生产执行依赖，也不保留独立 `connectOverCDP` 执行路径。

### 7.2 应删除的重复路径

完成能力对齐和回归验证后，移除：

- 生产代码中的直接 Playwright 浏览器执行依赖。
- 自定义多级 locator 回退链。
- AI 生成任意 CSS 临时脚本的执行路径。
- 重复的 `scriptExecutor`、`stagehandExecutor`、旧 `executorEngine` 和重复 agent。

删除必须分阶段进行；Stagehand 路径未通过等价验收前，旧路径保持只读回退能力，不继续扩展。

## 8. 后台任务与状态机

### 8.1 Rust 运行管理器

创建任务后立即返回 `runId`。Rust 后台运行管理器负责：

- 持久化状态和检查点。
- 调度单个专用浏览器和排队任务。
- 启动、监控和停止 Stagehand sidecar。
- 向前端广播任务事件。
- 处理暂停、继续、人工接管、终止和异常恢复。
- 无论前端页面是否存在，都继续维护任务状态。

### 8.2 状态流转

```text
queued -> preflight -> running -> passed
                              -> business_failed
                              -> blocked
                              -> pause_requested -> paused -> preflight/resume -> running
                              -> waiting_handoff -> preflight/resume -> running
                              -> cancelled
                              -> interrupted
```

规则：

- `preflight` 在锁定浏览器前完成配置校验、凭据引用校验、模型连通性检查和步骤编译。
- `pause_requested` 不立即打断原子浏览器动作；当前动作结束后写入检查点，再进入 `paused`。
- `paused` 和 `waiting_handoff` 必须解除浏览器输入锁，允许用户操作。
- 继续执行前重新校验 URL、登录会话、角色和关键业务状态，再重新锁定浏览器。
- 终止停止 sidecar 或进行中的 AI 请求，保存检查点，解除输入锁并进入 `cancelled`。
- 进程崩溃或应用异常退出后由 watchdog 解除输入锁，并将无法恢复的活动任务标为 `interrupted`。

## 9. 浏览器受控状态与交互保护

专用测试浏览器必须具有无法忽略的受控标识：

- 窗口标题和页面顶部常驻条显示“自动化执行中”、系统、环境、任务和当前步骤。
- 应用全局顶部显示高对比执行条，提供查看浏览器、请求暂停和终止按钮。
- `running` 时通过平台交互保护适配器阻止鼠标、键盘和导航干扰，仅保留紧急暂停/终止入口。
- 只有成功取得输入锁的任务才能从 `preflight` 进入 `running`。
- 暂停、人工接管、终止、阻塞或 watchdog 恢复时必须释放锁。

交互保护由本地平台适配器负责，不假设 Stagehand 提供操作系统级输入锁。任何无法取得或确认输入锁的情况都必须阻止自动执行，而不是在未保护浏览器中继续。

## 10. 凭据安全边界

- 账号表只保存 `accountId`、角色、环境、登录方式和 `credentialRef`。
- Windows 使用 Credential Manager，macOS 使用 Keychain 保存真实密码、令牌等秘密。
- 登录是独立于 AI 业务步骤的确定性流程。
- Rust 按 `credentialRef` 读取秘密，通过短生命周期本地载荷交给 sidecar；本地浏览器代码填充后立即销毁载荷。
- 密码、OTP 和令牌不得进入 AI 提示词、用例内容、生成脚本、日志、截图文本、事件详情或报告。
- 编译器必须识别并拒绝 `{{employeePassword}}`、`${password}` 等秘密占位符作为输入值执行。
- 多角色切换由运行编排器显式完成，AI 不生成登录或切换账号步骤。

## 11. 步骤编译与定位校验

AI 输出不能直接作为浏览器脚本执行。执行前必须编译为受限动作模型：

- 动作：导航、点击、填写、选择、等待、读取和断言等白名单操作。
- 定位：role、label、text、placeholder、test id 和经过语法校验的 CSS。
- 断言：存在性、可见性、文本、URL 和受限业务状态。

约束：

- 普通文本不能被当作 CSS 传给 `querySelector`。
- CSS 定位在进入执行器前完成语法校验。
- 首选语义定位；定位不唯一或无法解析时先使用 `observe` 获取候选。
- 无法可靠解析时进入 `waiting_handoff`，不得猜测并继续执行。
- `act` 和 `agent` 的每次调用都必须有明确目标、允许域名、最大动作数和超时。

## 12. 错误分类与重试

错误分为：

- `business_failed`：业务断言与预期不符，可生成缺陷草稿。
- `blocked`：模型网关 HTML 响应、429 限流、超时、网络、浏览器连接、配置或凭据引用不可用；可重试，不生成业务缺陷。
- `cancelled`：用户主动终止。
- `interrupted`：进程或应用异常中断且无法自动恢复。

模型调用采用有限次数指数退避和抖动。达到上限后写入可读阻塞原因、服务响应摘要和重试建议，不无限等待。AI 修复必须在安全暂停并释放浏览器输入锁后进行。

## 13. 全局执行中心、报告与问题

执行中心和报告页读取统一 SQLite 数据，默认展示所有系统，并提供系统、环境、状态和时间筛选。

每个终态任务都必须可见：

- 成功
- 业务失败
- 执行阻塞
- 已取消
- 已中断

报告至少包含系统、环境、需求版本、测试设计、套件、角色组合、步骤结果、失败分类、执行时间和返回设计详情的链接。

只有 `business_failed` 自动创建问题草稿和业务失败截图。基础设施阻塞、取消和中断不创建缺陷。截图及日志在持久化前执行秘密脱敏。

## 14. UI 改造

### 14.1 测试设计

- 左侧或顶部为当前系统、环境和设计列表。
- 详情区域显示需求版本、用例批次、确认状态和回归配置。
- 四阶段以生命周期导航呈现，显示数据状态、版本和更新时间，而不是仅用完成颜色表达流程。
- 当前阶段缺少数据时显示明确空状态，不借用其他设计或上次会话的数据。
- 需求变更后，旧用例显示“来源已过期”及重新生成入口。

### 14.2 全局执行提示

- 任何页面都显示活动任务条，不因切页消失。
- 执行条显示系统、环境、套件、进度和当前状态。
- `running` 显示暂停和终止；`pause_requested` 显示正在安全暂停；`paused` 显示继续、查看浏览器和终止；`waiting_handoff` 显示接管说明和继续校验入口。
- 控制按钮调用 Rust 运行管理器，不依赖当前页面组件状态。

## 15. 数据迁移

迁移流程：

1. 创建默认系统“试用期转正系统”。
2. 根据既有登录 URL 推断 `local` 或 `test`；无法判断的记录进入“待确认环境”迁移隔离区，人工归类前不写入正式系统环境和测试设计。
3. 既有用例按可识别来源聚合为测试设计；无需求来源的放入“历史导入设计单”。
4. 账号、账号组合、场景和套件补充系统、环境归属。
5. 将 JSON 文件和 localStorage 中的历史报告导入 SQLite，并标记为历史来源。
6. 升级时仍处于运行状态但无法恢复的任务标记为 `interrupted`。
7. 对数量、主外键、报告可见性和跨系统约束进行迁移校验。
8. 校验通过后保留可回滚备份；旧数据读取路径进入只读期，稳定版本后再删除。

迁移不得静默丢弃无法映射的数据。每条失败记录必须进入迁移结果并可人工处理；迁移隔离区不是第三种可执行环境。

## 16. 分阶段落地

1. **数据基础**：新增系统、环境、测试设计、版本和统一执行报告表，完成迁移器与只读兼容层。
2. **Stagehand 对齐**：建立受限动作模型和 Stagehand 执行适配器，用现有关键流程做等价回归。
3. **后台运行管理器**：迁移任务生命周期、事件、检查点、暂停/继续/终止和单浏览器队列。
4. **凭据与交互保护**：接入系统密钥库、专用浏览器标识、输入锁和 watchdog。
5. **UI 与报告统一**：上线测试设计列表/详情、全局执行条、统一执行中心和报告页。
6. **清理旧链路**：在迁移校验和能力对齐通过后，删除直接 Playwright、自定义 CDP、重复执行器和旧报告读取路径。

每一阶段都应可独立回滚。新旧执行路径并存期间通过功能开关选择，但同一个 `runId` 只能绑定一条执行路径。

## 17. 验收标准

- 仅测试设计页面按系统和环境隔离；执行中心、报告、问题和设置可查看所有系统并正确筛选。
- 本地和测试环境的数据、账号、套件和执行记录不会交叉组合。
- 需求来源刷新或重启后仍存在，四阶段数据始终属于同一个 `designId` 和需求版本。
- 切换左侧导航或刷新前端不会中断任务，重新进入可恢复实时进度和控制。
- 专用浏览器执行期间有明显标识且用户不能误操作；安全暂停后才可接管。
- 暂停、继续、人工接管和终止均遵守状态机、检查点和输入锁规则。
- 任何密码占位符或真实秘密都不会发送给 AI，也不会出现在用例、脚本、日志、截图文本或报告中。
- 普通文本不会作为 CSS 执行；无效或歧义定位在浏览器操作前被拒绝或转入人工接管。
- Stagehand 是唯一生产浏览器 SDK；不存在另一条直接 Playwright 或自定义 CDP 执行链。
- 模型 HTML 响应、429、超时和连接错误有限重试后进入 `blocked`，不误报业务缺陷。
- 所有终态任务都能在执行中心和报告页找到，且只有业务失败产生问题草稿。
- 历史用例和报告可查询，迁移对账通过，原始备份保留。

## 18. 文档与发布要求

实现阶段需同步更新架构、数据格式、Tauri 命令、配置、运行依赖、安装和打包文档。发布说明必须标明：

- 新的系统/环境归属和历史数据迁移行为。
- Stagehand sidecar 及其运行要求。
- 系统密钥库权限和专用浏览器交互保护能力。
- 旧执行链与旧报告读取路径的弃用和移除版本。

## 19. 代码与产物清理门禁

每个实施阶段完成后必须执行一次版本库清理审计，避免临时测试产物和已被替代的旧链路进入发布内容：

- 删除已被新实现完全替代且无回滚价值的旧生产代码、旧执行器、重复适配器和失效测试。
- 保留能够验证当前行为的正式自动化测试；测试代码不能仅因不进入生产包而加入 `.gitignore`。
- 将运行时生成且不可复现业务价值的文件加入 `.gitignore`，例如临时截图、录屏、跟踪文件、覆盖率输出、sidecar 临时状态、浏览器用户数据和本地迁移备份。
- 不得通过 `.gitignore` 隐藏已经被 Git 跟踪的旧代码；此类文件必须明确迁移、删除或保留并注明用途。
- 每次提交前检查暂存文件清单、忽略规则命中结果和构建产物，确保提交只包含本阶段需要上线的源代码、测试、迁移和文档。
- 每个阶段的验收记录必须列出“删除的旧代码”“新增忽略规则”“仍保留的兼容层及删除条件”。
